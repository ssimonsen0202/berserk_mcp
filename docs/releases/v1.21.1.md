# v1.21.1 — 2026-07-27

Fixes systematic token/cost over-counting across `claude_token_burn`,
`claude_cost_report`, and the AI FinOps usage pipeline (`spend_overview`,
`feature_cost`, `project_economics`, and related tools).

## Root cause

Claude Code writes one JSONL line per content block of a response
(`thinking`, `text`, `tool_use`, ...), and every block carries an identical
copy of that response's token usage. Nothing downstream recognized that
several rows can describe the same billable API call, so every tool that
summed tokens per row over-counted by a factor equal to however many
content blocks that response happened to have. Confirmed against real
session JSONL: two rows 3ms apart both `tokens_out=200`, sharing one
`message.id` but distinct `uuid`s — not a transport-level duplicate, a
logging-granularity mismatch. Full writeup in
`DUPLICATE_INGESTION_BUG_HANDOFF.md` and `PROPER_FIX_PLAN.md`
(`~/Library/Application Support/claude-otel-forwarder/`).

An earlier hypothesis in the same handoff (forwarder retry/timeout without
an idempotency key) was investigated and directly disproven — retried
copies would carry an identical `uuid`, and they don't.

## Fix

- **Forwarder** (`claude-otel-forwarder/forwarder.py`, not part of this
  repo): now captures `claude.message_id` on every assistant row.
- **`agent_analytics.py`**: added `_message_groups`/`_collapse_by_message`,
  grouping content-block rows by `(session_id, message_id)` before any
  token summation. Applied at every summing site —
  `analyze_token_burn_events`, `analyze_session_events`,
  `claude_cost_report`'s project grouping — plus a rewritten two-stage KQL
  aggregation in `_cost_daily_query`/`_cost_trend_query` so the day/model
  rollup collapses by message_id server-side before the final `sum()`.
- **`ai_finops.py`**: `deduplicate_usage_rows()` gained a second, distinct
  collapse pass for message_id — kept separate from its existing
  native/legacy exact-timestamp-fingerprint dedup, which solves an
  unrelated problem (two telemetry *sources* describing one request).
  `usage_aggregate_query()` gained a matching third KQL stage.
- Rows with an empty `message_id` (historical data ingested before the
  forwarder captured it) are never grouped with each other on any other
  key — a content/timestamp fingerprint was explicitly rejected as a
  grouping key because it risks silently dropping genuinely distinct calls
  that happen to share a token count and land close in time. Historical
  backfill is an open, separate, explicitly-approximate follow-up
  (`PROPER_FIX_PLAN.md` step 3), not shipped in this release.

## Verification

473/473 tests pass (465 baseline + 8 new regression tests — 5 in
`test_agent_analytics.py`, 3 in `test_ai_finops.py` — covering the two- and
three-content-block collapse cases from the handoff's real examples, the
different-message-ids-never-collapse regression case, and the
empty-message_id-rows-never-collapse-into-each-other case). Independently
confirmed against live production data collected after the forwarder
restart: the Python-side collapse (`analyze_token_burn_events`) eliminated
a 1.89x overcount on a live session (30 rows → 17 distinct calls, 24,973 →
13,202 tokens); the KQL-side day rollup (`_cost_daily_query`) eliminated a
1.95x overcount on the same window (37 → 20 events, 28,073 → 14,398 output
tokens) — both run directly against the fixed source functions and the
fixed query text executed live via `bzrk search`.
