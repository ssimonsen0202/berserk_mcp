# v1.37.5 — Schema snapshot read again; precise unknown-field check

Released: 2026-11-16

## What was wrong

**The schema snapshot was empty.** The bzrk CLI release of 2026-08-19 changed
its text table. Each row now starts with a row-index column, and the header
starts with `#` and gives each column as `Name:type`. The getschema parser
read the row index as the column name and rejected it, so it found no
columns. The fieldstats parser read numbers and version strings (for example
`0.2857…` and `0.31.0`) as field names. The cache stored this empty result
with the status `fresh`.

With no columns in the snapshot, `validate_kql` skipped the unknown-field
check. A query on a field that does not exist, such as `$time`, passed
validation and returned only empty values. Several hand-written queries
returned no data before anyone noticed the cause.

**The unknown-field check was not precise.** With a real snapshot, it would
have reported function names (`ago`, `dcount`), names that the query defines
(`extend share=...`, `summarize rows=count()`), make-series keywords (`step`)
and resource or attribute keys that the three-row sample did not contain.

## What changed

- The schema fetcher runs its four queries with `bzrk search --json` and reads
  the columns by name. The text parsers remain as a fallback. They skip the
  `#` header and the row-index column, and they accept only resource or
  attribute paths as field names, never bare numbers.
- `$raw` is a valid column name.
- When getschema answers, the snapshot also lists the top-level OTLP fields
  that the repository's own queries use (`body`, `severity_text`,
  `metric_name`, `value`, `trace_id`, `span_id`, `duration` and others),
  because getschema reports only five columns.
- A fetch that gives no columns raises an error. The caller then returns the
  last good snapshot as `stale`, or `unavailable`. It is never cached. A
  cached snapshot with no columns is fetched again, so the empty cache from
  the broken versions repairs itself on the next call.
- The unknown-field check ignores:
  - names followed by `(`;
  - names that the query assigns, including tuple assignments such as
    `(anomalies, score, baseline) = ...`;
  - words joined by `-` (`make-series`, `mv-expand`).
- A resource or attribute key that is not in the sample is reported only when
  it is a near match (ratio 0.85 or higher) of a known key, for example
  `service.nam` for `service.name`. A missing key alone proves nothing,
  because the keys come from a small sample.

## Known limits

- In a subtraction written without spaces (`end_time-start_time`), the check
  does not look at either name.
- The keyword and function lists in `kql_validation.py` are not complete. A
  KQL keyword that is not in them can be reported as an unknown field. The
  check is a warning and adds nothing to the risk score.

## Verification

New tests cover:
- the JSON output shape that bzrk returns;
- the text table with a row-index column;
- no numeric field names;
- the top-level fields;
- an empty fetch is not cached, and an empty cached snapshot is fetched again;
- the fetcher passes `--json`;
- `$time` and a made-up column are reported, and `$raw` is accepted;
- function calls, names the query defines, tuple assignments and hyphenated
  operators are not reported;
- unsampled bag keys are not reported.

One test runs every fixed query in the repository (more than 40) through the
check and expects no unknown fields.

Each fix was also undone on purpose, one at a time, to confirm that a test
fails. All mutations were caught.
