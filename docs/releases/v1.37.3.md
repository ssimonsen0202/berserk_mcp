# v1.37.3 — OpenRouter webhook receiver: 2xx, forward failures, signatures

Released: 2026-11-16

Three fixes to `evals/openrouter_webhook_receiver.py`, from a diagnosis
runbook written after a Berserk outage.

## What changed

**Any 2xx is a successful forward.** `post_to_berserk` returned success only
for HTTP 200. An ingest answer of 202 or 204 means the payload was accepted,
but the receiver logged every such forward as failed. It now accepts 200–299
and reports the status (`http 204`) in the detail.

**Forward failures are summarized.** Failures used to produce one stderr line
per delivery (`berserk forward failed: …` / `berserk forward raised: …`) and
nothing else, so a long outage wrote a line for every webhook. Those lines are
gone. A new `ForwardStats` counter (thread-safe) writes only:

- `berserk forward FAILING: …` on the first failure after success;
- `berserk forward still FAILING: N consecutive failures, …` at most every
  15 minutes while forwarding stays broken;
- `berserk forward RECOVERED after N consecutive failures …` when a forward
  succeeds again.

The webhook response to the sender still carries only `berserk_forwarded`
(true or false). Internal error text, which can name internal hosts, is not
returned. No HTTP status endpoint was added: behind a tunnel such as
Tailscale Funnel, public requests arrive from loopback, so a loopback-only
check would not keep them out.

**Signature checks.**

- The static check (`X-Webhook-Signature` equals the shared secret) now
  compares in constant time with `hmac.compare_digest`. The old `==` leaked
  timing on a publicly reachable endpoint. Non-ASCII header values are
  rejected, not a crash.
- New opt-in `--signature-mode openrouter-hmac` verifies
  `X-OpenRouter-Signature: t=<unix>,v1=<hex>`, an HMAC-SHA256 over
  `"<t>," + raw body`, accepted within 300 seconds. The scheme comes from
  OpenRouter's video-generation callback documentation. OpenRouter's
  Broadcast webhook documentation describes `X-Webhook-Signature` as a static
  custom header that the user sets, so the default stays `static` and
  deploying this release changes no behaviour.
- Both modes go through one verifier, `check_signature`, which returns
  `valid`, `invalid` or `absent`. Each mode reads only its own header. A wrong
  signature is always 401. An absent signature passes only the
  `X-Test-Connection` handshake, which never records or forwards its body.
  HMAC is computed over the raw request bytes, before JSON parsing. A
  timestamp longer than 12 digits is rejected before `int()`, so an oversized
  value answers 401 instead of dropping the connection. An unknown mode
  refuses to start.

## Review

A Codex review of the first commit found no P1 issues and three P2 issues,
all fixed in the second commit: unbounded `int()` on the HMAC timestamp,
per-delivery failure lines that defeated the bounded logging, and handshake
tests that did not check that nothing was written or forwarded.

## Verification

30 new tests in `evals/test_openrouter_webhook_receiver.py` cover 2xx and
non-2xx statuses, constant-time comparison, forged, stale, future,
re-serialized and malformed HMAC signatures, cross-mode headers, the
failure/recovery log lines, thread-safe counting and `main()` mode handling.
Run against the previous receiver, they fail: 202 and 204 are reported as
failures, `compare_digest` is never called, and `ForwardStats` and
`check_signature` do not exist.

All suites pass: `tests` 1,420 (1 skipped), `evals` 191, `ingestion` 23.
`make lint-ci`, `make format-check` and `make typecheck` are clean.

The new receiver was also run on the deployment host against its existing
`_http.py`: handshake 200, correct secret 200, wrong or missing secret 401,
a 204 from ingest reported as forwarded, one `FAILING` line for three
failed forwards, and HMAC mode checked against an independent `openssl`
signature (valid 200; tampered body, static header and stale timestamp 401).
