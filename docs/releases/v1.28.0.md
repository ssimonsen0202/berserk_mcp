# v1.28.0 — Model-behavior monitoring (drift/regression detection)

Released: 2026-09-03

A version-bump catch-up: the whole model-drift-monitoring feature (issues
#91/#92 and two rounds of independent Codex review) shipped across nine
commits without a version bump, sitting on `1.27.0` alongside an unrelated,
already-released feature. This release note covers all of it in one place.

## Why we built this

berserk-mcp reaches production models through an OpenRouter-style router:
the same model slug can sit behind a different backend provider or
quantization from one day to the next, and nothing about the model's *name*
changes when that happens. [`docs/berserk-dev-brief-2026-08-20.md`](../berserk-dev-brief-2026-08-20.md)
names the guardrail this requires at eval time — "pin the provider, disable
fallbacks... a sweep where the provider changed mid-run isn't a measurement
of the model" — but that guardrail only covers the one-time eval that picks
a model. Nothing watched whether the model *kept* behaving the same way
after it was chosen and deployed.

That gap matters specifically because of how this failure looks from the
outside. The same dev brief redefines berserk-mcp's whole success metric
around exactly this shape of problem: "**Silent-failure rate** — plausible,
well-formatted, undetectable without independent verification — **≤0.5%,
the only hard gate**." A model that quietly starts routing `top_cpu` instead
of `host_cpu` doesn't look broken. It looks like a normal tool call. Nobody
notices until the wrong answer has already cost someone real time, and by
then there's no way to tell whether it was a one-off or the new normal.

Before this feature, the only check against that risk was the router-cases
eval (`evals/router_cases.jsonl`) — run by a human, on demand, at model-
selection time. It answers "is this a good model to pick" once. It says
nothing about whether the model *still* deserves that pick a week later.

## Value

- **Makes an invisible failure mode visible and alertable.** A scheduled
  canary run scores the same `tool_accuracy` metric used to validate model
  choice in the first place, continuously, against production — not just at
  selection time.
- **Cheap relative to what it protects against.** ~$0.08 and 7.5–8.5 minutes
  per model per run (measured, 2026-09-01) — negligible next to the cost of
  a silent routing regression running unnoticed in production.
- **Calibrated against real data, not a guessed threshold.** The `0.02`
  noise band comes from 5 live canary runs (mean 0.9514, stdev 0.0049), so
  it clears ordinary API sampling variance without needing a wide enough
  band to also miss a regression that matters.
- **Separates signals for diagnosis, not just alerting.** A fingerprint
  change (behavioral/provider-metadata) flags "the provider changed
  something" independently of a score drop, and cohorting by
  `role`/`discovery_mode`/`tier` rules out "my own tool-schema config
  changed" before either gets blamed on the model.
- **Fails safe on missing or broken data.** A failed canary run is recorded
  as a failure, never scored as zero, so a provider outage can't masquerade
  as a catastrophic quality collapse — and (after the second fix pass below)
  a broken result read can't masquerade as "all models stable" either.
- **Protects a deliberate cost/accuracy tradeoff.** Model-tier selection
  elsewhere in this project is a validated tradeoff between cost and routing
  accuracy. Without this feature, that tradeoff could silently stop holding
  the moment the provider changed something underneath the chosen tier, with
  no signal that it had happened.

## New tools

- **`model_drift_check`** and **`model_drift_history`** — MCP tools that
  classify a model's tool-routing accuracy over time against a calibrated
  noise band, using measured stdev/range from 5 live canary runs
  (`DEFAULT_NOISE_BAND = 0.02`, mean 0.9514, stdev 0.0049, range 0.0139) to
  tell real drift apart from run-to-run noise. Verdicts: `insufficient-data`,
  `stable`, `degrading`, `step-change`, each carrying a confidence level and
  a human-readable reason.
- **Canary CLI** (`evals/canary.py`) — runs the existing eval harness against
  a live model on a schedule, emits scored results as OTLP records
  (`eval.*` attributes, gated by `EVAL_ATTRIBUTE_ALLOWLIST`), and records
  `eval.role` / `eval.discovery_mode` / `eval.tier` so an environment change
  (different tool-schema restriction) is never mistaken for a model
  regression under the same `case_set_version`.
- **`--drift-report`** (`run_drift_report()` in `berserk_mcp.py`) — a
  standalone CLI entry point that queries recent canary results, classifies
  every model with enough history, and alerts (stderr + Discord) on any
  `degrading`/`step-change` verdict.

## Design

- Three separate signals stay separate rather than collapsing into one
  verdict: scored canary accuracy, behavioral/provider-metadata
  fingerprints, and trend analysis (`MIN_TREND_R2`). A verdict only escalates
  past `stable` on a sustained drop (`CONSECUTIVE_REQUIRED = 2` runs) beyond
  the noise band, not a single noisy sample (`MIN_HISTORY = 4` minimum runs
  before any verdict is attempted at all).
- Cohort selection is scoped to the current `case_set_version` + `role` +
  `discovery_mode` + `tier` combination — mixing runs across a tool-schema
  change would misread environment drift as model drift.
- Confidence caps at `low` when the observed `repeats` count is below the
  band's own calibration (`MIN_RELIABLE_REPEATS = 3`) — the verdict still
  fires, but flags itself as less trustworthy rather than silently reporting
  high confidence off an under-sampled run.

## Independent review

Two rounds of independent Codex review, both fully re-verified by direct
execution (not just reading the diff) before and after each fix, per the
"verify by running it" discipline recorded in
[`docs/claude-code-review-feedback-loop.md`](../claude-code-review-feedback-loop.md)
fault #10:

- **First review** (10 findings, 2 P1 / 8 P2) — fixed in `dbcd7d4`. Included
  a NameError in a rarely-hit branch, a cohort-selection gap that let
  different `role`/`discovery_mode` runs get compared against each other,
  a hardcoded query table that ignored `BERSERK_TABLE`, and an incomplete
  return path in the canary-run CLI that could fall through into serving
  the MCP server instead of exiting.
- **Backtest of that fix** — caught that the fix for the NameError-adjacent
  JSON-parsing bug had traded a crash for a silent `{}`, which made
  `--drift-report` read a genuinely broken result identically to "no data"
  and print "All models stable" on exit 0. Also found a fingerprint-change
  comparison that missed a transition landing exactly at the baseline/recent
  window boundary, and confirmed `BERSERK_MCP_TIER` was missing from the
  cohort key (`role`/`discovery_mode` were fixed, tier was an
  identically-shaped gap). Fixed in `35750fc`:
  - `group_by_model()` now raises a dedicated `BzrkResultParseError` instead
    of returning `{}`, caught explicitly by `model_drift_check`,
    `model_drift_history`, and the newly-extracted `run_drift_report()` —
    "absence of evidence is a failure," not silent success.
  - `_fingerprint_changed()` is now derived from the same
    `baseline_rows`/`recent_rows` split `classify()` already computes for
    its accuracy comparison, so both signals read from consistent windows.
  - `BERSERK_MCP_TIER` was added to the cohort key in both
    `model_drift.py` and `evals/canary.py`.
  - Both dispatcher tools now render fingerprint status in their output —
    their tool descriptions already promised it, but neither branch
    surfaced it until this fix.
- A third backtest pass, of `35750fc` itself, is in progress — Codex hit its
  usage limit mid-run; see
  [`docs/codex-backtest-handoff-2026-09-03.md`](../codex-backtest-handoff-2026-09-03.md)
  for where to resume it.
