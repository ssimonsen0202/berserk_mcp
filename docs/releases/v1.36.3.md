# v1.36.3 — Complete multi-day cost totals

Released: 2026-10-03

## What was wrong

`claude_spend_overview` and the other AI FinOps reports undercounted any
window longer than about one day. This was true before v1.36.2 too.

The usage query's first `summarize` keeps about 40 columns for each group.
Over more than about a day, it reaches Berserk's 10 MB summarize memory
limit. Berserk then drops the groups that do not fit. It still returns status
200, and it reports the drop only in the response's `warnings`:

> Summarize memory limit reached (10.0 MB). Kept 1861 groups, additional
> groups were not collected.

`ai_finops` did not read `warnings`, so it reported the short total as
complete. Example: for 2026-09-28, local transcripts show 302 API calls and
103,567,572 cache-read tokens. A 5-day window counted 142 calls and
66,145,531 cache-read tokens. A 1-day window, which stays under the limit,
was correct.

## What changed

`_fetch_usage`, which all eight AI FinOps report paths use, now:

1. Runs the usage query once for the whole window.
2. Reads the response's `warnings`. A warning kind that contains "Limit" or
   "Truncat" means the result is incomplete.
3. On such a warning, halves the window and queries each half, down to one
   hour. The halves touch at one instant, so no record is counted twice or
   missed.
4. Fails with a clear message if a one-hour slice still hits the limit, or if
   the window cannot be split. It never returns the partial rows.

A window under the limit still costs one query. `usage_aggregate_query`
takes an optional absolute window (`start`, `end`) for the slices.
`ai_finops.configure` takes `since_hours`; `berserk_mcp` passes
`finops_since_hours`, which uses the same `since` normalization as
`bzrk_search`.

## Verification

Live, against the same cluster:

| Window | Day | Calls | Cache-read tokens | Output tokens |
|---|---|---|---|---|
| 5 days, before | 2026-09-28 | 142 | 66,145,531 | 183,747 |
| 5 days, after | 2026-09-28 | 302 | 103,567,572 | 352,238 |
| Local transcripts | 2026-09-28 | 302 | 103,567,572 | 352,238 |
| 30 days, after | 2026-09-13 | 1,092 | 292,723,425 | 679,062 |
| Local transcripts | 2026-09-13 | 1,090 | 292,723,425 | 679,062 |

On 2026-09-13, the token totals match exactly. The report counts 2 more
events than there are API calls, because API-error events count as events
but carry no usage.

A 30-day window took 75 seconds. An MCP client with a shorter request timeout
can time out on very wide windows. Use a narrower `since` in that case.

## Tests

`tests/test_finops_memory_limit.py` (6 tests): one query when the window fits;
a wide window split into slices that touch, with every event counted once;
fail closed when the smallest slice or an unsplittable window hits the limit;
which warning kinds count; and the absolute-window query filter.
