# v1.37.8 — `save_query` checks for rows and refuses duplicates

Released: 2026-11-17

`save_query` used to save any query that ran without error. A query with a wrong
field name ran fine, matched zero rows, and entered the store as if it worked.
This release closes that gap and stops duplicate saves.

## What changed

- **Zero-row check.** After the verification run, an empty result triggers one
  more run over `24h ago`. The retry uses the same `bzrk` call, so the query
  slot and the window budget apply. If the retry also returns nothing, the
  query is not saved. The error says the query matched nothing in 24 hours,
  that a bare column name silently matches zero rows, and that
  `discover_schema` shows the real field names. If the retry fails, nothing is
  saved and the usual "NOT saved - the query failed when verified" error
  appears, with the `bzrk` text fenced.
- **What counts as empty.** The `(no rows)` sentinel, a JSON result with no
  rows, a JSON result with one value equal to zero, and a text result of at
  most one data row whose last token is zero. A text table of several rows that
  ends in `0` is not empty. The helpers are `result_row_count` and
  `result_is_empty` in `berserk_mcp/tools.py`. The result envelope for the
  simple tools uses `result_row_count` and its output is unchanged.
  `count_result_is_zero` is unchanged.
- **`allow_empty`.** New optional boolean argument. Only a JSON `true` counts,
  as with `overwrite`. On an empty result the entry is saved with
  `rows_verified: false`. On a non-empty result the entry gets
  `rows_verified: true` and `rows_verified_at`. The entry keeps the caller's
  `since`, not `24h ago`. Entries written earlier have no `rows_verified` and
  count as verified.
- **Success text.** `Saved '<name>'. Verified: returned rows.` or
  `Saved '<name>'. NOT verified to return rows (allow_empty).` The old
  "verified, returned data" text is gone.
- **Fingerprint.** `learned.kql_fingerprint` hashes the KQL after it collapses
  whitespace outside quoted text. It does not fold case or strip comments.
  Every write stores `kql_sha256` and `kql_fp_v: 1`. A stored hash with another
  or missing `kql_fp_v` is ignored and recomputed from the entry's `kql`.
- **Duplicate refusal in `save_query`.** The same fingerprint under another name
  is refused, and the error names the existing entry. Only entries the caller
  can see count, so a hidden entry is never named. `overwrite=true` does not
  bypass this. Two concurrent saves can still both succeed, because the check
  runs outside the store lock.
- **Duplicate handling in the pipeline.** `persist_learned_query` for a
  generated entry with the same fingerprint under another name writes nothing
  and returns `action: "duplicate"` with `duplicate_of`. The same name with the
  same KQL as a stored generated entry returns `action: "unchanged"` and keeps
  its status and approval. The discovery job report gains a `duplicates` list.
  A job whose queries are all duplicates ends `done`.

## Compatibility

An existing `learned.json` loads and behaves as before. The old fingerprint
fields are additive. `save_query` now refuses a query that returns no rows
unless `allow_empty=true`.

## Verification

New tests are in `tests/test_learning_loop_save.py`. A few older tests changed
because their bzrk stubs returned one header-less line, which now counts as
zero rows, or because they saved the same KQL under several names.
