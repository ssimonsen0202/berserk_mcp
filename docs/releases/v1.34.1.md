# v1.34.1 — Refused HTTP requests get their status on Windows

Released: 2026-09-26

## What changed

- **Refused requests are drained before the reply.** When the HTTP transport
  refuses a request (403 for a bad Host, Origin or token, 404, 415, 429), it
  now reads and discards the request body before it sends the status. Before,
  it replied and closed with the body unread. Windows then resets the
  connection, and the client saw `ConnectionAbortedError` (WinError 10053)
  instead of the status. This made the v1.32.0 DNS-rebinding test fail
  intermittently on the Windows CI runners.
- **The drain is bounded.** It reads only a body whose `Content-Length` is at
  most `BERSERK_MCP_HTTP_MAX_REQUEST_BYTES`, and it stops at an absolute
  two-second deadline. A client that stalls, or sends one byte at a time,
  cannot keep a handler thread busy for longer. The socket's previous timeout
  is restored afterwards.
- **411 and 413 are not drained.** These refusals have no bounded body
  length, so the server still replies and closes at once.

## Tests

- A unit test checks the body is consumed, out-of-range lengths are left
  alone, and the socket timeout is restored.
- Socket tests check that the 403, 404 and 415 replies wait for the whole
  promised body, and that a stalled or trickling body is cut off at the
  deadline. Mutation checks confirmed each test fails without the part of the
  fix it covers.
- `_discard_request_body` is registered in `tests/security_reviews.json`.
