# v1.37.9 — save_query cannot see or replace a hidden saved query

Released: 2026-11-17

## What changed

- **The name check respects visibility.** `save_query` looked for an existing
  saved query of the same name across the whole store. A caller in one role
  therefore learned that a name existed in another role ("already exists").
  With `overwrite=true` it replaced that entry and moved it to its own role.
  The same held for a generated query that the small tier cannot see.
- **The fix.** A name held by an entry the caller cannot see gets a short
  refusal: "The name '<name>' is not available. Choose another name." The
  reply is the same whether a role or the tier hides the entry, and
  `overwrite=true` does not change it. The store write checks again under its
  lock, so a concurrent write cannot slip past the handler's check.
- **Refused before any query runs.** The check runs before validation and the
  verification query, so a hidden name costs no Berserk query.
- **Generated writes and `review_generated`.** A generated write no longer
  replaces a generated entry that the active role cannot see; it takes a
  `_gen` name instead. `review_generated` lists and returns only entries the
  caller can see.
- **Known limit.** Names are shared across the whole store. A caller can still
  tell that a name is taken, because a free name saves and a taken one is
  refused. The caller learns nothing else about the entry. Roles scope which
  tools a client sees; they are not a secrecy boundary between tenants.
- **Not changed.** The role that owns an entry can still replace it with
  `overwrite=true`. Generated writes keep their own rule: they never replace a
  human entry and take a `_gen` name instead.

## Verification

`tests/test_save_query_hidden_name.py` adds eight tests. Seven failed before the
fix; the eighth guards that the owning role can still overwrite.
