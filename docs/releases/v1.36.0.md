# v1.36.0 — Bounded output

Released: 2026-10-02

This release has three efficiency fixes from a code review. The first fix
also removes a risk: one `search` call could fill the model's context, or
overflow it.

## A limit on search and saved-query results

`search`, `run_saved`, and every `saved__<name>` tool run user-written KQL.
Validation warns when such a query has no `take` or `top` bound, or a bound
above `BERSERK_MCP_KQL_MAX_ROWS`. The query still runs. Before this release,
the server then sent the whole result to the model. The only limit was
`BERSERK_MCP_MAX_RESULT_BYTES` (10 MiB). That setting protects the process,
not the context window.

These three paths now send at most `BERSERK_MCP_MAX_OUTPUT_CHARS` characters
(default 40,000, about 10k tokens):

- The server cuts a `bzrk --json` result of up to 1,000,000 characters by
  whole rows, from the start. The result stays valid JSON with the same
  columns.
- The server cuts larger JSON, table text from a `bzrk` build without
  `--json`, and unknown shapes at a line break.
- The server does not change a result that is within the limit.
- After the closing `<untrusted_log_data>` tag, a note gives the rows or
  characters that the model received. The note also suggests `take`, a
  narrower `where`, or `summarize`. The server builds the note only from
  counts, so the note stays outside the fence.
- The server cuts the result before it fences it, so the fence is always
  complete.
- `0` turns the limit off.

This change does not affect the analytics tools. They parse full results to
calculate totals, so the limit applies only where raw results go to the model.

`.semgrep/fence-untrusted-data.yml` lists `_fence_limited` (cut, then fence)
as a new sanitizer, next to `_wrap_analytics` and `_envelope`. A canary check
confirms that the rule still flags an unfenced return. It also flags a result
that the code cut but did not fence. `tests/security_reviews.json` records
the function.

### Security review

A Codex Security scan of the first version (scan `5053dc0c`, partial
coverage) found the semgrep sanitizer sound. It found two low-severity memory
faults in the cut. This release fixes both:

| Finding | Before | After |
|---|---|---|
| 1. The JSON path decoded the whole result before it cut it | 8 MB tiny-row result: about 209 MB extra | 0.04 MB |
| 2. The text path split every line before it cut the text | 10 MB of short lines: 44 to 71 MB extra | 0.04 MB |

- The server decodes JSON only up to 1,000,000 characters. That costs at
  most about 26 MB. For a larger result, the server cuts the text instead,
  and the note says that the result was too large to cut by rows.
- The text cut finds the last line break within the limit. It does not split
  the whole result.
- The server releases the query slot when `bzrk` exits, so the cut now takes
  a slot again. With the default of 2 slots, at most two cuts decode at the
  same time. If no slot becomes free in 10 seconds, the cut uses the text
  path, which does not decode.
- JSON that is nested deeply enough to raise `RecursionError` now goes to
  the text cut. The request does not fail.

Nobody has scanned these fixes again.

## Compact JSON tool output

Eight return paths sent indented JSON (`indent=2`) to the model: `find_tool`,
`validate_kql`, `self_check`, `generate_parser`, `review_generated`, and the
CanonLoom bridge tools. They now use compact separators. On a `find_tool`
answer, the output is 32% shorter. The content does not change.

CLI output (`--doctor`, the `--export-bi` manifest, `--agent-report-json`) and
the HTML dashboard stay indented, because people read them.

## A limit on the result cache and the fail-cooldown table

Before this release, an expired cache entry stayed until the same query came
back. A long-running server (the HTTP transport) therefore kept every
distinct result that it had answered. The fail-cooldown table had the same
problem.

Each insert now removes the expired entries. It then removes the oldest
entries above `BERSERK_MCP_CACHE_MAX_ENTRIES` (default 256). You cannot turn
this limit off: `0` gives the default.

## Upgrade notes

- New settings: `BERSERK_MCP_MAX_OUTPUT_CHARS` and
  `BERSERK_MCP_CACHE_MAX_ENTRIES`. See [configuration](../configuration.md).
- If a client parsed the exact whitespace of the eight JSON outputs, it must
  parse them as JSON instead.
- Tests: `tests/test_output_budget.py` has 25 tests. Memory tests reproduce
  both scan findings. Three tests call through `dispatch()`, where the output
  redactor runs. They check that the redactor still removes credentials from
  the compact JSON. With redaction off, these three tests fail, so they
  detect a leak.
