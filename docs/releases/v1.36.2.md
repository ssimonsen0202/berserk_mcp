# v1.36.2 — Usage corrections

Released: 2026-10-02

## What changed

`usage_aggregate_query` (the source of `claude_spend_overview`) now reads two
services: `claude-code` and `claude-code-usage-correction`.

Before 2026-10-02, the Claude Code log forwarder sent only input and output
tokens. Cache reads and cache writes are most of Claude Code's cost, so the
older history in Berserk understates cost. A *usage correction* is one record
per older API call. It is built from the original transcript line, with the
full token usage and a short body.

The query merges each correction into its call:

1. The first `summarize` groups by `dedupe_key`. A correction has the same
   session, timestamp, model, and token counts as its original row, so it
   gets the same key.
2. The second `summarize` groups by `message_id`.

Both stages take `max()` of each column. The call keeps its cache tokens and
still counts once. If Berserk never received the call, the correction stands
for it.

The corrections use their own `service.name`, so no other tool counts them as
events. The session, error, tool, and search tools read only `claude-code`.

## Verification

On 2026-09-28, local transcripts show 302 API calls, 103,567,572 cache-read
tokens, and 352,238 output tokens. After the corrections for that day, the
query's merge stages return the same three numbers. The full backfill sent
14,405 corrections (13,383 distinct calls). Their cache-read total in Berserk
equals the local total, 6,105,610,902 tokens.

## Known limit: multi-day windows

Berserk keeps at most 10 MB of groups in one `summarize`. Over more than about
one day, the first `summarize` of this query reaches that limit. Berserk then
drops groups and returns a `SummarizeMemoryLimit` warning, which this release
does not read. So `claude_spend_overview` undercounts windows longer than
about one day. This was true before this release too. A fix is planned.

## Tests

`test_usage_query_reads_usage_corrections` checks that the query reads both
