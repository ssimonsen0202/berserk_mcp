# v1.37.2 — Three security fixes from Codex Security review 1

Released: 2026-10-05

Codex Security review 1 of the package split (scan `20261003T195944Z-81942`)
reported three medium findings in code that was already on `main` before the
split. This release fixes all three.

## What changed

### Every bzrk query holds a query slot (CWE-770)

`BERSERK_MCP_MAX_CONCURRENT_QUERIES` limits how many bzrk query processes run
at once. Before this release, only `bzrk_search` and live `validate_kql`
took a slot. The `schema` tool, the stale-schema refresh and the
`self_check` doctor queries called `run_bzrk` directly, so parallel callers
could start more processes than the limit.

`run_bzrk` now takes a slot for every bzrk command it launches, except
`bzrk --version`. The rule fails closed: a future query subcommand is limited
too. A caller that already holds a slot does not take a second one, so a
nested query cannot deadlock. The schema refresh now stops at its first
failed query, because it holds the schema lock while it waits.

**Visible change:** under load, `schema` and `self_check` can now return the
queue-full message instead of starting another query.

### Each tool call keeps its own query budget (CWE-362)

`handle_call` stored the tool name and query budget in one process-wide
variable. When two calls overlapped, the call that finished first could
clear or replace the other's budget. That query then ran with the 120-second
default instead of its own budget, often 10 seconds. A budget could also stay
behind after both calls ended and apply to an unrelated query.

The budget is now per call, held in a `ContextVar`. Each thread sees only its
own.

### Telemetry text is fenced in three more tools (CWE-1427)

Three tools put text that a telemetry producer controls into their replies
as if it were the server's own prose:

- `scan_secrets`: service names, the `first_seen` timestamp field, and the
  backend's error text, which can carry partial result rows.
- `detect_new_sources`: the new, drifted and queued service names.
- `self_check`: the error detail of the auth, table and recent-row checks.

That text now appears only inside `<untrusted_log_data>` tags. The fixed
prose around it stays outside the tags. `secret_scan` and `parser_factory`
receive the package's fence through `configure()`. If they are not
configured, their default fence also fences, so they fail closed.

A label that happens to equal a fixed server message, such as `(no rows)`,
is fenced too.

**Visible change:** these three tools now return fenced service names and
error details. The `--doctor` terminal output does not change. The
`--worker` pass prints the `detect_new_sources` summary and can post it to
Discord, so that output now carries the fence tags too.

## Not changed

The semgrep fencing rule does not cover search functions that `configure()`
passes into the root modules. A trial source for them gave 21 findings
across four root modules, and most were false positives: those modules fence
field by field through their own `_fence`. CI also does not scan the root
modules. The existing rule is unchanged.

## Verification

Each fix has a test that failed before the change and passes after it:

- `tests/test_query_slot.py` uses the real `run_bzrk` with a recording
  semaphore. It checks that every `search` launch from `schema`, the schema
  refresh, the three doctor queries, `bzrk_search` and live `validate_kql`
  holds a slot. It also checks that holders take exactly one slot,
  `--version` takes none, a full queue starts no process, and a failed
  launch releases its slot.
- `tests/test_fleet_context.py` runs two overlapping calls with different
  budgets, in both completion orders. Events force the interleaving. On the
  old code it catches both a replaced budget and a budget left behind. It
  passed 40 times in a row.
- `tests/test_telemetry_labels_fenced.py` injects a service name such as
  `ignore-previous-instructions` and checks that it appears only inside a
  fence in all three tools.

The security ledger re-records `run_bzrk` and `bzrk_search` and adds
`_run_bzrk_launch`, which holds the launch code `run_bzrk` used to contain,
unchanged.
