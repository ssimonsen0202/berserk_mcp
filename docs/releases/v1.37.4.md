# v1.37.4 — OpenRouter webhook receiver: fast reply and no duplicate spans

Released: 2026-11-16

Two problems in `evals/openrouter_webhook_receiver.py`, found on the first real
deliveries after a Berserk outage.

## What was wrong

**Most spans arrived twice.** Of 12 distinct spans delivered in one test
session, 9 were delivered two times, 2 to 9 seconds apart. The receiver
waited for Berserk's ingest before it answered OpenRouter. Ingest takes about
two seconds to answer, plus the time to redact long prompts, so OpenRouter
treated the delivery as slow and sent it again. The retried copy was recorded
and forwarded a second time, which double-counts tokens and cost in Berserk.

**A full disk dropped the connection.** When the capture file could not be
written, the handler raised, the connection closed without a reply, and
nothing told OpenRouter to try again.

## What changed

- **The reply goes out right after the local capture is written.** Redaction
  and the forward to Berserk run on two background workers behind a bounded
  queue (200 deliveries). The response now says `"berserk_forward": "queued"`,
  `"skipped"` (nothing new to forward) or `"dropped"` (queue full), instead of
  `"berserk_forwarded": true|false`. OpenRouter ignores the field. A dropped or
  failed forward loses nothing: the delivery is in the local capture, and the
  backfill script can send it later. A full queue is logged through the same
  `FAILING` / `RECOVERED` lines as other forward failures.
- **Each `(traceId, spanId)` is handled once.** A retried delivery stays in the
  raw capture (which records every delivery) but is not written to the spans
  file or forwarded again. The response reports `"duplicates_skipped"`. The set
  is bounded (5,000 pairs, oldest evicted). A span without both ids is never
  treated as a duplicate.
- **The claim happens before the write and is released if the write fails.**
  Two simultaneous copies of one span cannot both pass, and a retry after a
  real failure is processed, not skipped.
- **A storage failure answers `500 {"ok": false, "error": "storage failure"}`**
  so OpenRouter retries, and logs the cause.
- A payload that is valid JSON but not an object, or has an unexpected shape,
  is kept in the raw capture and answered `200 {"parsed": false}` instead of
  crashing the handler. Any other failure after a span is claimed releases the
  claim and answers the same way, so a retry is never mistaken for a duplicate.
- A claim can be released only by the delivery that made it. If a claim was
  evicted and a retry re-claimed the span, a late release from the first
  attempt does nothing.
- Each delivery's rows go to the spans file in one write. If that write fails
  part-way, the file is cut back to its old size, so the retry cannot leave
  duplicate rows.
- A `total_tokens`, `input_tokens` or `output_tokens` value that is not a whole
  number no longer drops the span. The row keeps `null` for that field and the
  raw value stays under `attributes`.
- A forward worker survives any exception, including one raised by its own
  logging or counters.
- A request body larger than 16 MiB is refused with `413` before it is read.

## Known limits

- The duplicate set holds 5,000 spans. A retry that arrives after more than
  5,000 other spans is treated as new.
- If two copies of one span arrive within milliseconds and the first copy then
  fails to write, the second copy has already been answered `200`. The span is
  missing from the spans file and from Berserk, but the raw capture has it and
  `openrouter_backfill_to_berserk.py` can send it.
- A restart empties the queue and the duplicate set. Queued forwards are lost
  the same way (recoverable from the local capture).
- The reply field changed from `berserk_forwarded` (true or false) to
  `berserk_forward` (`queued`, `skipped` or `dropped`), and `spans_received`
  now counts only new spans. Nothing in this repository reads either field.

## Verification

New tests cover: the reply returns while a forward is still blocked (no
wall-clock threshold); a duplicate delivery is recorded once and forwarded
once while the raw capture keeps both; overlapping payloads forward only the
new spans; a full queue still replies and records; a failed write gives 500
and the retry is processed; a half-finished write is rolled back; a stale
release cannot remove a newer claim; a failure after the claim releases it; a
worker survives a counter failure; an oversized body is refused. The existing forwarding tests were adapted to the
background worker (they now wait for the queue to drain and use distinct span
ids).

Each behaviour was also broken on purpose in a scratch run to confirm the
tests fail: dedupe off, claim not released, stale release allowed, reply
waiting for the forward, full queue never dropping, write errors not caught,
no rollback of a partial write, workers dying on a counter error, no body size
cap, and a bad token count being fatal. Every mutation was caught.

## Review

A Codex review of the first version found no P1 issues and seven P2 issues.
Five were fixed in this release (claim leak after an extraction error, stale
release, partial-write duplicates, worker survival, unbounded body size) and
the wall-clock assertion in one test was removed. The concurrent-duplicate
race and the changed reply field are documented above as known limits.
