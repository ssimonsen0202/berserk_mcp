# v1.33.0 — Symlink- and race-safe store files

Released: 2026-09-26

Closes findings 3 and 5 of an earlier Codex Security scan of `_store.py`, the
shared module every private store (saved queries, parser state, schema
snapshots, FinOps stores, discovery queue) uses.

## The problem

`validate_store_path` checked and resolved a path once, but every later
operation looked the path up again by name:

- **Finding 5:** validation resolved a symlink at the store file itself, so
  reads and writes went wherever that symlink pointed.
- **Finding 3:** a parent directory swapped for a symlink between validation
  and use redirected the temporary file, the atomic rename, reads, `chmod`
  and lock-file cleanup. `FileLock` also removed whatever file sat at the
  lock name on exit, even one another process had created.

Both need an attacker who can already write to a directory above the store,
and stores live in `0700` per-user directories, so the exposure was limited.

## What changed (POSIX)

- `validate_store_path` resolves the parent directory but keeps the file
  name as given, so a symlink at the store file is no longer silently
  followed.
- Reads, atomic writes and lock files open the parent directory one
  component at a time with `O_NOFOLLOW`, then create, `fchmod`, rename, read
  and unlink relative to that open directory, with `O_NOFOLLOW` on the file.
  A symlink anywhere in the path now fails the operation
  (`StoreRedirectError`; a read logs and returns an empty store).
- `FileLock` on POSIX is now a kernel lock (`fcntl.flock`) on a lock file
  opened without following symlinks. The kernel releases it when the holder
  exits or crashes, so a lock is never broken as stale: the documented
  lost-update race after a 30-second suspension no longer exists on POSIX.
  The lock file is kept, not deleted, since deleting it would reopen that
  race. Windows keeps the lock-file protocol.
- Private directories the module creates get their `0700` mode through a
  no-follow descriptor, not a second path lookup.
- AI FinOps' business-data import and recommendation-decision recording now
  hold the store's file lock for the whole read-modify-write. They only held
  an in-process lock, so two berserk-mcp processes could overwrite each
  other's update (found in review; older than this release).
- The AI FinOps pseudonym key, business store and decision store read
  through the same no-follow path (`_store.read_private_text`) instead of
  plain `open()`. A symlinked pseudonym key now fails closed: a planted link
  can no longer substitute a known key and make pseudonyms predictable.

Windows keeps the previous behaviour: Python has no directory-relative file
calls there, and the per-user DACL on private store directories is what keeps
other users from planting links.

## A macOS kernel race found while testing

On macOS, creating a file through a directory descriptor (`openat` with
`O_CREAT`) can fail with ENOENT when another thread creates the same name at
the same moment: about 1 open in 9 with 16 threads, while an ordinary
path-based open never fails. Under 20 contending threads this lost roughly
one store update in eight rounds. Create-opens now retry that error a
bounded number of times (one retry was always enough in 6,400 trials). A
threaded contention test guards it and fails when the retry is removed.

## Upgrade notes

- If you pointed a store file at another location through a symlink, set the
  store path to the real location instead; a symlinked store file is now
  refused.
- `*.lock` files now stay next to POSIX stores after use. They are empty
  kernel-lock anchors; leave them in place.
- Restart every berserk-mcp process on a host together: an older process
  still uses the lock-file protocol and does not see the new kernel lock.

## Testing

`NoFollowStoreTest` plants a symlink at the store file (read and write),
swaps the parent directory for a symlink after validation, plants a symlinked
lock file, holds the lock from a second process (timeout), kills that
process (the kernel releases the lock), and checks leftover lock files,
descriptor leaks, atomicity and file modes. Against the previous
`_store.py`, four of these fail: it read through the symlink, wrote through
it, was redirected by the parent swap, and removed another process's lock
file.
